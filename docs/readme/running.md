# Running Shutter: more detail

The README's Try it section has the commands. This page keeps the detail that does not fit there.

### Notes on the install

- On Windows, run `install.sh` in Git Bash or a WSL 2 shell (Docker Desktop's WSL integration); PowerShell isn't supported by the installer.
- On Apple silicon, pass `--image-file` the `irishealth_arm64-community` file of the same build (the replay edition's public image has an ARM64 build too); Shutter has not been run on ARM64 yet.
- The first `up` builds the image in 2 to 15 minutes, depending on the machine: 14.5 minutes on 8 cores and 5 GB of memory, most of it in the install step. The replay edition builds in about 8 minutes on that machine; on a 12-thread VM with 11 GB of memory it built and was healthy in 2 minutes 4 seconds from a fresh copy, with `--no-cache` and the public image already pulled (3 November 2026; the 6 GB image download comes first on a new machine).
- Measured on 8 November 2026 with the base image already on the machine, from `install.sh` to healthy: the replay edition 2 min 21 s, build 154 2 min 30 s and build 109 2 min 52 s, on the test VMs; the six IPM commands on a stock 154 image took 2 min 20 s. Downloading an image comes first and is not counted.
- **Which build a plain `./install.sh` takes:** with only build 154 loaded, it uses 154; with both 109 and 154 loaded, it uses 109. `install.sh` reads `SHUTTER_IMAGE` only from `.env`, never from the shell, so for 154 run `cp .env.example .env`, set `SHUTTER_IMAGE=irishealth-community:2026.3.0AI.154.0` in it, and run `./install.sh`.
- **Switching editions:** run `docker compose down -v` first (it removes the instance's data), then remove `.env` or change `SHUTTER_IMAGE` and `SHUTTER_WITH_AIHUB` in it: `install.sh` refuses an `.env` set up for the other edition.
- The ports are published on `127.0.0.1` only, because the demo's passwords are well known; from another machine, use an SSH tunnel (`ssh -L 52773:localhost:52773 <the Docker host>`). `SHUTTER_WEB_PORT` and `SHUTTER_SUPERSERVER_PORT` in `.env` change the ports; with no `.env` yet, set them before the command (`SHUTTER_SUPERSERVER_PORT=1973 ./install.sh --replay`) and `install.sh` keeps them in the `.env` it creates. `install.sh` checks both before it changes anything, and `docker compose` takes a value in the shell over `.env`'s.

### Users

| User | Can |
| --- | --- |
| `operator` | View cases and incidents, run scenarios, reinvestigate a case, draft and send escalations, mark a case handled by the team (unless the site profile asks for an approver to close a case), and start a production review |
| `approver` | Everything `operator` can, and approve or reject plans and incident releases, read the message traces and the Workflow inbox, save the site profile, change the agent library, mark a case handled where the site profile needs an approver for it, and mark a review's finding intended |

Neither user starts, stops or purges the production.

One Shutter per Docker host: the container is named `shutter` and its image `shutter:dev`. To run a second beside it, clone into another folder and add a `docker-compose.override.yml` there with its own `name:`, `container_name:` and `image:`, and other ports.

To feed a message of your own, copy an HL7 file (one message, `.hl7`) into the production's inbound folder in the data volume: `docker cp my-message.hl7 shutter:/usr/irissys/mgr/shutter/in/`. Without a key, a failure it causes takes the rules path, unless the catalogue gives it to the board or a person: then it goes to a person with no plan (see [Limits, plainly](https://github.com/MxSalata/shutter#limits-plainly)).

### More about running it

The first `up` creates the `SHUTTER` namespace, installs the InterSystems Package Manager (from the pinned installer kept in `vendor/ipm`, so the build does not depend on the package registry) and loads Shutter: on the AI Hub image the `iris-shutter` package (the production, the case store, the gate, the downstream system, the web application, the recorded agent runs, and the live agents with their knowledge bases), and on the public image the core module in `core/` (`iris-shutter-core`, everything but the live agents). A step that fails stops the build with `BUILD FAILED` and the reason. The production starts with the container, and as it starts it clears two known startup alerts (the build host's "failover" message and the preview build's own startup error), so Docker's health check reflects the instance's real state; any other alert stays.

To watch a case unfold, run a scenario from the web application's Scenarios page (36 in all: S1 to S34, with S23 in three parts, each in [scenarios.md](https://github.com/MxSalata/shutter/blob/main/docs/readme/scenarios.md); S11 and S12 are the outage scenarios that open an incident, S19 fails in the demo hospital's own production, in S20 a nurse moves the patient by hand in the downstream system while the resend waits for approval, S21's transfer is timed in the hour that happens twice when the clocks go back, in S22 the same overtaken transfer fails at the bed manager, which closes its case with no write, and at the patient records system, whose case asks for its history to be corrected by hand, S23a to S23c are a bed another patient holds, S24 a newer message on its way as the resend is due, and S25 a message with the site's own segment, read by the Second Parser): each one feeds synthetic ADT messages into the production, makes one delivery fail in a particular way, and opens a case. With an `ANTHROPIC_API_KEY` in `.env`, the production writes the provider configuration from it when it starts, and the agent items, set to `auto`, then run live (`SHUTTER_AGENT_MODE` forces `live`, `record` or `replay`). Measured on 25 October 2026 with `claude-opus-5-5`: one board pass (three specialists and the coordinator) uses about 72,000 input and 4,200 output tokens, roughly 0.38 USD at list prices, and takes 24 to 32 seconds from the board's start to the coordinator's plan, because the three specialists run in parallel; the Settings page shows the figures per run, whose durations add up to more.

What you make stays: the cases, approvals, incidents, the site profile and Shutter's record of the provider configuration live in a data database inside the `shutter-mgr` volume (the image keeps only the code), so `docker compose down` and `up` keep them, a rebuilt image brings new code to the same data (after a rebuild, run the install once as [docs/INSTALL.md](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md) section 8 says, so new production items are added; a build that changes the gate's policy version, as 1.2.0 did with `2026-11-07.1`, voids approvals given before it and not yet dispatched: such a case blocks at dispatch with `APPROVAL_POLICY_CHANGED`; reinvestigate it), and `docker compose down -v` starts afresh. A build from before 1 November 2026 put the data database inside the container rather than the volume, so its cases don't survive a rebuild. A volume made by a build from before 18 October 2026 has no data database, and one from before 19 October 2026 keeps the downstream system's records under its earlier name, which newer builds don't read, and one made by an earlier build without the demo hospital has no `HOSPITAL` namespace: remove such a volume once (`docker compose down -v`) before the first `up` of a newer build. The compose file gives the container two minutes to stop (`stop_grace_period`), so IRIS writes its journal and write image out cleanly; a container killed mid-write recovers from the journal at the next start, which is what the "abnormal shutdown" alert in the console log then says. When the production starts it re-reads the knowledge files that changed (block reasons, catalogue, site profile seed, recordings, and the documents the agents search), so a rebuilt image's knowledge reaches the kept data; a site profile saved from the app is never overwritten by the seed. Installing again over an instance that already has Shutter (a rebuilt image on the kept volume, or `zpm "load"` again) brings the roles to their current definition and the demo users `operator`, `approver`, `forwarder` and `downstream-client` back to the demo's role, password and enabled state, and rewrites the `DownstreamAPI` credential; a non-demo install only adds roles to users that exist. Every install also removes what the downstream system was called before 19 October 2026: its web application, resource, roles, user, credential and classes, when they are there.

**What reaches the model.** Only what is needed leaves IRIS: before the evidence or a tool result goes to an agent, identifiers found in known fields are replaced by per-case tokens (`MRN-T1`, `ENC-T1` and the like, mapped back only inside IRIS) and matched exactly elsewhere, so one that appears only in a receiver's or engine's free text can reach the model, the demographics (names, date of birth, sex, address) are dropped, and each OBX or NTE note becomes a flag saying that free text is present and whether it reads like an instruction; the text itself goes only when the site profile's `model_content.free_text` is true. `SELECT Shutter_Util.ModelView_Preview('C-000012')` shows what the model would see of a case, and `tests/privacy_check.py` fails when a recording carries a name, a date of birth or a raw identifier.

**Escalation by email.** When Shutter cannot recover a case (blocked, escalated or failed), the case page drafts an email for the team that owns the receiving system, from the stored case and without a model: the hospital number, the NHS number and the date of birth, the event and its operation key, what failed, why Shutter stopped, what the receiver holds, the encounter's timeline and what Shutter sent; no name, address or note text. A person edits it, picks the team (the site profile's `teams`) and sends it; the send is bound to the digest of the text they read. The `Escalation Mail` operation sends through the site's mail server when its `SMTPServer`, port, TLS and credentials are set in the production (first-time configuration; the NHS relay at most trusts), and otherwise writes an `.eml` file under `<mgr>/shutter/out/mail` and shows it as saved, not delivered (nobody was emailed; once a mail server is set the same text can be sent), so the demo and CI need no mail server. Every recipient must be one bare address inside the site's allowed mail domains (`mail.allowed_domains`; with none set no email can go; the shipped profile allows `example.nhs.uk`, its teams' domain), a subject with a line break is refused, and nothing is sent about a case once it is closed or reopened. Ninety days after the case closes (`SHUTTER_ESCALATION_DAYS`; `0` keeps them) the retention task removes the email's text and the `.eml` file; the escalation stays on record with its digest, recipients and who sent it.

**The feed's time zone.** HL7 timestamps that carry no offset are read in the site profile's `feed.time_zone`: `Europe/London` (the shipped profile, with British Summer Time, so 09:20 on 15 October is 08:20Z), `UTC`, a fixed offset such as `+01:00`, or any IANA zone name this IRIS knows (`Europe/Paris`, `America/New_York`), read through Embedded Python's `zoneinfo`; without `zoneinfo` such a zone is refused, and a time in it is read as UTC with a warning. The zone changes every operation key, so set it before the first case; the matcher's `event_time` condition and the gate then block a resend whose event time precedes its admission, lies in the future, is far from when it was recorded, or, with no offset, sits within an hour of a clock change in the feed's zone. Such a time is not simply bad data, so a person decides (E13): one more than a day before it was recorded is usually a retrospective entry (paper notes typed in later), one in the future or before the admission a clock fault or a mistyped time, and one without an offset near a clock change may be an hour that night holds twice (or never), so only the source can say when it was.

**A site install (no demo).** The image is the demo. On a hospital's own IRIS for Health, create a dedicated `SHUTTER` namespace as [INSTALL section 3](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md#3-shape-a-shutter-in-its-own-namespace) says (load `src/Shutter/Setup.cls`, create the namespace, `zn "SHUTTER"`, load IPM there), then load the module with the demo switched off: `zpm "load /path/to/shutter -Ddemo=0"`. Don't use `src/Shutter/Installer.cls` for this: it also makes the demo's namespaces. The install starts in shadow mode, and sends no rehearsal, recovery write or escalation email until a person enables recovery. That install creates the resources and roles, the web applications `/api/shutter` and `/shutter`, the Workflow role "Shutter Approvers" and the retention task, and starts `Shutter.Production` with its demo items (`ADT In`, `ADT to Downstream`, `Downstream Out`, `ADT to Records`, `Records Out`, `Scenario Player`) switched off; it makes no demo users and nothing of the demo receiver, imports no recorded runs, and creates no message purge task unless `SHUTTER_MESSAGE_PURGE=1` (the purge keeps `SHUTTER_MESSAGE_DAYS` days, 90 by default; the installer reads both when it runs, the image build from `.env` through the compose file's build arguments). The hospital's own productions then hand Shutter their failed deliveries: each adds `Shutter.Intake.Forwarder`, which posts a failed message with its context to `POST /api/shutter/intake` as a user holding `Shutter_Forwarder`, and Shutter opens the case with the source recorded. The full guide for an integration team, both shapes, is [docs/INSTALL.md](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md).

**Shutter watching a production it does not own.** The image also creates the `HOSPITAL` namespace, the demo hospital whose production is not Shutter's: `PAS In` on `<mgr>/shutter/hospital/in`, `PAS to Downstream`, `Downstream Out` to the demo bed-management system, and `Shutter Forwarder`. It starts with the container; a delivery that fails there appears in Shutter as a case that names its source (namespace, production, route and the message's header), with Shutter's own copy of the message in its evidence, and a resend goes through Shutter's connector. Its messages and settings live in a data database of their own in the same volume. To see it, run S19 in Site policy mode, then open the Management Portal in the namespace `HOSPITAL`, production `Hospital.Production`: the transfer's Visual Trace shows `PAS In`, `PAS to Downstream`, the failed call of `Downstream Out` and the `Shutter Forwarder`'s post to Shutter's intake.

**A production review.** One read-only pass over a production Shutter runs or watches (its own `Shutter.Production`, the demo hospital's `Hospital.Production`, any that has sent it a case): the effective value of every setting that decides whether a failure fails forward, is seen and stays in order (`FailureTimeout`, `RetryInterval`, `ReplyCodeActions`, `Framing`, `AlertOnError` and `AlertGroups`, the queue alerts, `InactivityTimeout`, `ArchiveIO`, `PoolSize`, `Enabled`), resolved through the item, the system default settings and the class default and saying which answered; the message purge task; and the window's suspended and failed messages, event log errors grouped by signature and rule errors, each tied to the cases Shutter opened for the item. Twenty-three checks, each with a severity and, kept apart, an evidence confidence (confirmed, consistent, indicative), in a deterministic order (severity tier, unique cases, recency); with an API key the review agent ranks them within their tiers and explains each against the case history, and without one the deterministic order stands and the answer says so. An approver can mark a finding intended, bound to a fingerprint of the exact configuration, so it stays quiet until the value moves. The review never changes a production: a person applies any change in the Management Portal. To try it, as `operator`: `GET /api/shutter/production-reviews/targets` lists the productions a review may be asked for, and `POST /api/shutter/production-reviews` with `{"production": "Shutter.Production"}` (or `{"namespace": "HOSPITAL", "production": "Hospital.Production"}`, the hospital's production read in its own namespace), with `X-Requested-With: Shutter` and an `Idempotency-Key` as on every POST, starts one and answers its id; `GET /api/shutter/production-reviews/{id}` shows the findings once its `state` is `done`, and `POST /api/shutter/production-reviews/{id}/annotations` as `approver` marks one intended. In the Management Portal the run is the `Case Review` item's message in the Visual Trace.

**Inside a production you already run.** Shutter's items can live in an existing production instead of `Shutter.Production`: load the core classes into that namespace and run `SELECT Shutter.Setup_InstallInto('Your.Production', '/path/to/shutter/')` (or `zpm "load /path/to/shutter -Ddemo=0 -Dproduction=Your.Production"`). It adds the case workflow, the incident workflow, the evidence collector, the gate, the verifier, the escalation mail, the Workflow operation, the API service, the index, the intake and the agent operations to that production as `Shutter.Production` defines them, writes their default settings for it and updates it in place when it is running; it never stops it, creates no demo users or receiver and no message purge. The health report then names that production.

**The HL7 schema and the triggers.** Each HL7 service parses with its own schema category, as IRIS does (the demo's `ADT In` uses 2.5.1; a site's route sets 2.3.1, 2.4 or its own custom category, or one category per message type), and Shutter reads the fields it needs by position, which are the same in 2.3.1, 2.4 and 2.5.1: MSH, EVN, PID-3, PV1-2, -3, -19 and -44, MRG for a merge. The evidence notes when the message's own version (MSH-12) differs from the route's category; it is a note for the conformance review, never a failure. The feed maps these ADT triggers: A01, A02, A03 and A08 are delivered to the downstream system as the admission, transfer, discharge and update they are, A06 and A07 (a change of patient class) as updates that carry no location (an A06's new location in PV1-3 is not passed on), and an A04 registration as an admission only when it names an inpatient with a bed; registrations without a bed, pre-admissions (A05) and person events (A28, A31) are recorded in the exact index, where the case page's timeline shows them between the movements, and are not delivered. Any other trigger opens a case that says the message could not be mapped, and that includes common ones: A15 and A16 (a pending transfer or discharge), A17 (a swap of two patients' beds), A21 and A22 (leave of absence and the return from it), A47 (a change of patient identifier) and A54 (a change of attending doctor).

**Merges and cancellations.** By default Shutter never touches an ADT^A40 merge: the message is withheld, a case opens with the surviving and prior identifiers, the gate refuses any resend (`MERGE_WITHHELD`), and the escalation draft goes to the team the site profile names for the sending application (`teams[].sources`), the PAS team as a rule. A site whose risk tolerance allows it sets `merges: allowed` in the profile and `merges: true` on a receiver that takes merges. Cancellations (A11, A12, A13) are delivered only to a receiver whose entry says `cancels: true`; the demo's downstream system cannot reverse an event, so a cancellation is withheld and escalated (`CANCEL_UNSUPPORTED`). Once a team has corrected the receiver by hand, `POST /cases/{id}/close` with a reason (the case page's "Mark as handled by the team") closes the case with the reason and who closed it on its record. An operator closes it, since the escalation is the sign-off; a site that wants an approver to close a case sets `approvers.close_needs_approver` in the site profile, and then only an approver does. The case page's evidence shows the version note as `message_version`, `route_category`, `route_standard` and `version_agrees`, and the timeline names registrations, pre-admissions and person events by those words. A withheld case never convenes the board, whatever the mode.

Other settings are in `.env.example`: the published ports, the agents' mode and model, and the installer's demo password and message purge.

**Spend, in full.** A storm of one kind convenes one board: the cases with the same failure signature within ten minutes follow its lead, each through its own gate and approval. `BoardsPerMinute` (6) spreads the others out, a run over its token budget is not used (the budget is judged after the run), and `SHUTTER_DAILY_BUDGET_USD` stops new live runs once the recorded spend and reservations reach a day's live spend, or the next run's estimate no longer fits what is left. After that a case the catalogue gives to the board or a person goes to a person with no plan, and others take the rules path: set it on any instance with a key.

### The knowledge in IRIS vector tables

`Shutter.Knowledge.Library.TableFor(collection)` names each collection's vector table `Shutter_Knowledge.<collection>`; `%AI.RAG.VectorStore.IRIS` (384 dimensions, model `AllMiniLML6V2`) creates it with the columns `id` (the chunk's digest), `text`, `vector`, `metadata` and `source` (the Markdown file), and a `<collection>_Config` table beside it. On a fresh install on build `2027.1.0AI.109.0` (4 November 2026): `contracts` 26 chunks, `lifecycle` 17, `effects` 11, `playbooks` 20, `review` 57 and `explain` 83.

In the Management Portal's SQL page (namespace `SHUTTER`), the interface contract's chunks nearest its own rule WIC-3.1 ("Only a receipt proves that an operation was committed"), by cosine similarity of the stored embeddings:

```sql
SELECT TOP 3 b.id, SUBSTRING(b.text, 1, 120) AS chunk, ROUND(VECTOR_COSINE(b.vector, a.vector), 3) AS similarity
FROM Shutter_Knowledge.contracts a, Shutter_Knowledge.contracts b
WHERE a.text LIKE 'WIC-3.1.%' AND b.id <> a.id
ORDER BY similarity DESC
```

On build 109 the first is WIC-5.2, the receipts route (0.747), then WIC-2.5, the dry run (0.690). Across collections, `FROM Shutter_Knowledge.contracts a, Shutter_Knowledge.playbooks b` finds the recovery playbook's RP-3.1, "The receipt decides whether a movement was committed" (0.663).

The query compares stored embeddings. A fresh phrase can't be embedded from SQL on this build: `%AI.RAG.Embedding.FastEmbed` embeds only inside AI Hub's own bridge (its `EmbedBatch` throws "use the Rust bridge directly", AI Hub bug report #8), and `%AI.RAG.KnowledgeBase` has no search of its own. So a phrase search is the agents' tool (`search_contracts` and the other five, `TopK` 4), which the Visual Trace shows as a tool call of a run.

### Agent runs by board member, in SQL

In the Management Portal's SQL page (namespace `SHUTTER`): every agent run's tokens and cost, by board member, model and mode (live or replay).

```sql
-- Agent runs, tokens and cost by board member, model and mode
SELECT %EXACT(MemberCode) AS Member, %EXACT(Model) AS Model, %EXACT(Mode) AS Mode, COUNT(*) AS Runs,
       SUM(PromptTokens) AS Prompt, SUM(CompletionTokens) AS Completion, ROUND(SUM(CostUSD), 4) AS CostUSD
FROM Shutter_Store.AgentRun
GROUP BY %EXACT(MemberCode), %EXACT(Model), %EXACT(Mode)
ORDER BY Member, Mode
```

### Other limits

- The shipped site profile asks a person to approve every resend, at every tier (interleaved chains go to the board, whose plan a person then approves). A demo install keeps the earlier table as the demo's own setting, labelled on the Site profile page: it releases the single cases the catalogue settles at tiers 1 and 2 without asking a person, and the online demo asks a person at tier 2. A non-demo install also starts with no demo receiver, and a tier releases by policy only once its profile says so: a real site first answers the profile's induction questions.
- An order or result case gets its findings (who holds the message, the receiver's own words and the result they name) and escalates to a person before any model runs; nothing is resent from the case. At a receiver set up for it (`engine_resend`), an outage's messages that never arrived are listed, and after one approval Engine Resend sends them again through the engine, each settled by the engine's delivery outcome and the receiver's declared duplicate handling, not verified at the receiver ([CONTRACTS 17.8](https://github.com/MxSalata/shutter/blob/main/docs/CONTRACTS.md#178-the-send-v151-to-v154)).
- A06 and A07 (a change of patient class) are delivered as an update with no location, although an A06 can carry a new location in PV1-3.
- Closed cases are kept (the record is the product); only the escalation emails' text and `.eml` files go, 90 days after the case closed (`SHUTTER_ESCALATION_DAYS`), and a site that wants finished cases removed switches the case purge on in the Task Manager: a case still waiting for a person stays.
- A case left in a working state by a restart in the middle of a scenario is noted when the production starts (an error-kind event on the case saying so, with the way out), and once nothing of its workflow has moved for 15 minutes an approver can abandon it (`POST /cases/{id}/abandon`, or "Abandon the case" on the case page): the case fails with disposition `abandoned` and can be reinvestigated. Nothing abandons a case by itself, and a case that is merely waiting (a message in flight, an approval task open) is refused with 409 `busy`.
- A production review reads one production at a time and only the ones Shutter knows (its own, and the ones its cases came from); the reply code and framing checks need an HL7 TCP item, which neither demo production has, so when the server reports none the page says "No HL7 TCP item in this production" rather than leaving it to read as no finding.
- The production review's agent never runs live on an instance without a provider: it replays a recording made on the demo's canonical configuration (the record key is the configuration findings' fingerprint), or the page shows the deterministic findings alone with no explanation. The checks are the review; the agent only orders and explains them.
