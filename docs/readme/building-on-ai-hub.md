# Building on AI Hub and Interoperability: what worked, what was hard

What I found building Shutter, measured on build `2026.3.0AI.154.0`; the longer story is [article 1](https://community.intersystems.com/post/building-shutter-iris-ai-hub-what-worked-what-was-hard-and-what-it-cost). On `2027.1.0AI.109.0`, `Run()`'s three arguments, the bare `object`, the `RebuildRegistry()` step, `As %Status` and the missing IPM still hold; the rest wasn't re-run. Each row of the table says which build it was seen on.

- **Worked well:** typed tools (a `%JSON.Adaptor` parameter gives the model a full JSON Schema and arrives as an instance, so a terminal tool refuses a bad result with reasons); the two policies; FastEmbed knowledge bases, built from Markdown in about 11 seconds; prompt caching.
- **Licence:** the Community licence's connections run out under cookie-less HTTP bursts, so scripts keep one cookie.
- **Interoperability, worked well:** every agent run and approval is a production message and each tool call is in the trace's log, so the Visual Trace and the Message Viewer already show a case end to end.
- **Interoperability, hard:** a production sends its alerts to the one item named `Ens.Alert`, so the alert intake either takes that name and passes every alert but the consumer's own on to the site's own consumer, or sits as a target of the site's alert router; a Workflow task's form can be filled by the process, but a filled digest would always match, so Shutter leaves it empty and an inbox approval must paste it, or it binds nothing.
- **Interoperability, would like to see:** a production setting that names more than one alert target, so a watcher can hear every alert without changing the site's `Ens.Alert` item, which today must be the watcher itself or route to it.

| IPM in the image | 154, 109 | The image has no IPM (`%IPM.Main` isn't there). | The image build loads IPM 0.10.10 from the installer kept in `vendor/ipm`, checked against its SHA-256 first. | IPM in the AI Hub image. | [iris.script](https://github.com/MxSalata/shutter/blob/main/iris.script) |
| Typed tool arguments | 154, 109 | When a tool's argument has several properties of one `%JSON.Adaptor` class, `%Discover()` describes the first in full and the rest as a bare `{"type": "object"}`, so the model doesn't see their fields. | The `SubmitBoardAnswer` tool's description spells out `setting`, `under_alternative` and `suggested_change`, three properties of one schema class. | Every such property described in full, or through one shared `$ref`. | [SubmitBoardAnswer.cls](https://github.com/MxSalata/shutter/blob/main/src/Shutter/Tools/SubmitBoardAnswer.cls) |

Found with a reproduction, not filed yet:

- Typed tool arguments: properties that share one schema class reach the model as a bare `object` (154, 109).
- Config Store descriptors: a fresh instance can't create an `AI.LLM` configuration until the registry is rebuilt (154, 109).
- `%LogExecution` on 109: [#4](https://github.com/intersystems-community/ai-hub-eap-bugreports/issues/4) reports it on 154, and nothing there says 109 behaves the same.
