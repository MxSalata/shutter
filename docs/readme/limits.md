# Limits, plainly

For a clinical safety officer: [the hazards, data flow, threats and what a site still owes](https://github.com/MxSalata/shutter/blob/main/docs/SAFETY.md).

The README's "Limits, plainly" states eight; this page has every limit, in full, with its effect, what a site can do about it, and its status. Scenarios: [scenarios.md](https://github.com/MxSalata/shutter/blob/main/docs/readme/scenarios.md); what each row of "What can go wrong when you resend" doesn't cover: [edge-cases.md](https://github.com/MxSalata/shutter/blob/main/docs/edge-cases.md); limits of a running instance: [running.md](https://github.com/MxSalata/shutter/blob/main/docs/readme/running.md#other-limits).

**Status:** *By design*, Shutter does this on purpose; *Open*, not handled yet; *Measured*, the effect was measured, as the row says; *Untested*, nobody has tried it.

## Every limit

| Limit | Effect | Workaround | Status |
| --- | --- | --- | --- |
| **Not measured at a hospital** | How many of a hospital's failures Shutter resolves has not been measured: the scenarios are written by us and the data is synthetic, and until a receiver is given an API, help means a case and a drafted email (and, at a receiver set up for it, an outage's resend through the engine). | [Pilot it first](https://github.com/MxSalata/shutter/blob/main/docs/readme/first-steps.md#pilot-it-first), with no receiver given an API. | Open |
| **A site class in the demo's packages** | Shutter's module carries the demo hospital's classes in the `Hospital` and `Downstream` packages. Loading it in a namespace that already holds a site class of the same name, `Hospital.Production` for example, overwrites that class, and the package manager's uninstall removes the whole `Hospital` package. | Install into a namespace of its own, or one whose classes don't use those two package names; the installer refuses those names as the production to watch. | Open: the demo packages are renamed in a later release |
| **The receiver is a demo** | The receiver is a demo bed-management system built for the scenarios. A case resends only to a receiver whose API (state, receipt, capabilities and operations paths) the site profile describes; an outage's resend, at a receiver set up for it, goes through the engine instead. Every proof is against the demo receiver or a stub. | Treat recovery as a demonstration until a site has tested its own receiver against [the receiver contract](https://github.com/MxSalata/shutter/blob/main/docs/readme/receiver-contract.md). | Open |
| **A plain MLLP receiver's case gets no resend** | An ACK says a message arrived, not what the receiver now holds: a NACK or a lost connection on a stock `EnsLib.HL7.Operation.TCPOperation` with `AlertOnError` on opens a case through the alert intake, and a person gets the evidence and the reason nothing was sent (`tests/e2e/plain_receiver_check.py`). With `AlertOnError` off and no forwarder, nothing opens a case: if the receiver's site profile entry has a `watch` block, the outage watch still reads the item from the engine and opens an outage while its listener is down, with the failed messages listed, but no case. The one resend such a receiver can get is outage recovery: with `watch` and `engine_resend` in its entry, one approval has the engine resend the messages that never arrived, completed in the engine and settled by the receiver's declared duplicate handling, never verified at the receiver ([CONTRACTS 17.8](https://github.com/MxSalata/shutter/blob/main/docs/CONTRACTS.md#178-the-send-v151-to-v154)). | Set `AlertOnError` on what you want watched; the Doctor names an item with it off (`alert_on_error_off`). | By design |
| **The shipped site profile asks a person** | It asks a person to approve every resend, at every tier (interleaved chains go to the board, whose plan a person then approves). Before that, a new install with no demo, and an upgrade whose profile doesn't say, starts in shadow mode: Shutter investigates, reading a receiver's state and receipts where its API is described, and records what it would propose, and sends no rehearsal, recovery write, resend preview or outage resend until the site profile's `recovery.mode` says `enabled`. Enabling it releases no plan made before: such a case is reinvestigated. At a tier a site's own policy releases, a resend writes with no approval. A demo install keeps the earlier table as the demo's own, labelled setting, releasing single cases at tiers 1 and 2, and the online demo asks a person at tier 2 ([more](https://github.com/MxSalata/shutter/blob/main/docs/readme/running.md#other-limits)). | A site decides its tier table before any receiver gets an API. | By design, since 1.1.0 |
| **Without an API key, the agents replay** | Recorded runs are replayed. A case with no recording, such as one from your own HL7 file, takes the rules path, where the gate alone decides and a resend waits for a person; a case the catalogue gives to the board or a person goes to a person instead, with no plan. | `ANTHROPIC_API_KEY` for live agents. | By design |
| **When the model fails** | A run that fails, runs out of time or is refused gives no findings, and Shutter doesn't retry it or try another model. The case goes to a person with no plan; or the coordinator plans from the findings in hand; or, when nobody could answer and the catalogue doesn't ask for the board or a person, the rules path proposes the plain resend. Such a plan waits for a person's approval whatever the site's policy, so nothing is written unless a person approves it. One call is bounded at 120 s, a run at 8 turns and 120,000 tokens, and the board at 600 s for the specialists, then 600 s for the coordinator; on build 154 a run's own deadline isn't checked during the run. As read in the code, a key the provider refuses doesn't set the 15-minute breaker: each run still calls the provider and ends `model_error` ([every status and what the case does](https://github.com/MxSalata/shutter/blob/main/docs/readme/model-fails.md)). | `SHUTTER_PROVIDER_TIMEOUT_SECONDS` sets the bound on one call; keep a hard limit at the provider. | Measured on 1.1.1 (every specialist `model_error`, build 109) and 1.2.0 (no recording, replay); the other statuses read in the code, and the breaker is Open |
| **Nobody is told** | By default nothing tells anyone that an outage opened. Since 1.3.0 a site can add Outage Mailer and switch it on per receiver; without it the site's own alert must carry the link ([the install guide, section 11](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md#11-a-receivers-outages-v110)). After 24 hours with no decision an approval task is cancelled and the case moves to `escalated`, with no mail or alert. A site can turn on a scheduled reminder mail for cases left open (`reminders` in the site profile, off when absent). In shadow mode no reminder or escalation email goes unless the profile says `"notifications": {"shadow_delivery": "enabled"}`, and enabling recovery sends no escalation email that shadow mode held: a person sends it again. | Someone watches the Workflow inbox and the case list; the site's own alerting carries the outage link. | Open |
| **Receivers' outages (v1.1.0)** | Shutter watches configured HL7 TCP operations without contacting their receivers. It groups outages, shows whether the engine is retrying or messages have settled, preserves unresolved exceptions, and shows the site's next action and contact. Since 1.4.0, at a receiver set up for it (`engine_resend`), one approval has the engine resend the outage's messages that never arrived, orders and results included, each settled by the engine's delivery outcome and the receiver's declared duplicate handling rather than verified at the receiver; elsewhere it sends nothing. At supported stock TCP routes, it also prevents Shutter's ADT API recovery from competing with the engine's delivery. A listener that comes back for long enough to drain the queue closes the outage, so a flapping listener at a retrying receiver makes one outage, and one queue wait case, per time it goes down (measured: 3 in 5 minutes for three 20 s returns). At a no-retry receiver with `AlertOnError` on, a case opened after the outage has gone to a person is not linked to it (measured: 16 of 24 in a 5-minute flap); those cases stand on their own. | The site's own alert carries the outage's link. | Measured |
| **A large incident is approved once, and its task lists only the first chains** | The shared approval task's Workflow message holds 2,000 characters. Above about four chains it lists the first whole chains that fit (the first 3, measured at 12 and at 500 chains), how many chains and operations it leaves out, and the incident page, which has them all; the plan digest is never cut, and one approval binds every chain the plan holds, listed in the message or not. 1.1.1 and earlier abandoned such an incident instead, with every case `failed`. Measured on IRIS for Health Community 2026.2 and the AI Hub build `2026.3.0AI.154.0`, with one shape of storm (fresh patients, an admission and a transfer each) and the receiver in the same instance: 40 and 200 failures grouped into one incident, approved once and released whole at about 3 s an item (about 2 minutes at 40, 10 minutes at 200), no key twice, each write after its gate and rehearsal. At 1,000, intake, grouping, the one task and the first 50 items held; the whole release, about 50 minutes by extrapolation, was not run. An error raising the task no longer closes the incident: it waits for a person, an alert names it, and the workflow tries again every 5 minutes ([the measurements](https://github.com/MxSalata/shutter/blob/main/docs/readme/storm-at-scale.md#after-the-fix)). | The incident page lists every chain; approve there or in the Workflow inbox. | Measured; a restart during a release, a slow receiver and a storm through the board are unmeasured |
| **Incidents** | A chain waiting on a bed held for another chain of its incident stops, and its later items go to a person; the waiting case then runs alone under the site's policy for a single case. An item closed with nothing written has no receipt, so the next item takes the version read at verification. Any error in the incident's workflow during a release, other than raising an approval task, abandons the whole incident: a released case it can't find again, or a failure moving on to the next item, stops its open chains and fails its cases not yet past investigation, with the reason. A receiver that goes down again during a release stops each remaining chain in turn: the released item's preflight read, tried four times, or its write finds the receiver down, the case stops for a person and that chain's later items go to a person, then the next chain stops the same way. No write is retried blindly, so nothing is written twice. | | Open |
| **Orders, results and documents** | Up to 2 MB they get a case and a drafted email, never a resend from the case (an order or result case also carries its findings); larger gets an alert and no case. The one exception is a receiver with a document profile, switched on at both ends: the forwarder sends a failed MDM (T01 to T11), or an ORU carrying a report as an attachment, as metadata only, so the 2 MB limit on a forwarded message doesn't apply and the case opens with no copy of the message. "At any size" means that limit is lifted, no more: Shutter never receives the document, and a whole message posted to the intake is still refused over 2 MB ([the install guide, section 9.10](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md#910-document-exceptions)). An outage's undelivered orders and results can be resent after one approval at a receiver set up for it. | A person acts on the case. | By design |
| **A transport ACK, then lost downstream** | A message accepted by a transport ACK and then lost downstream raises nothing in Shutter: on stock settings a commit ACK completes exactly as an application ACK does, which we measured ([the install guide, section 9](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md#9-onboarding-several-namespaces)). | | Measured |
| **A write whose answer was lost** | It is judged at the last read, about 70 s after the attempt by default: with no sign of it by then, the outcome is unknown and a person decides, because a slower receiver can still commit it. The case says not committed only when the version has moved past the one the write was conditional on, by something else. | A site with a slower receiver raises `UncertainSettleSeconds`. | By design |
| **An operation that retries for ever** | At `FailureTimeout` -1, at a receiver that also has an API, Shutter refuses the resend while the engine is trying, and closes the case when the engine delivers (measured on 109). A site's own operation class isn't read that way. | Keep `FailureTimeout` 0 at a site's own operation class. | Measured |
| **A case waiting on the engine** | It is judged by the Case Releaser every few seconds; while the engine's record can't be read it stays blocked. | The Doctor counts it in `release_sweep.engine_unreadable`. | By design |
| **Further messages are read, not held** | At each write Shutter reads every HL7 message since the case's own, for up to 30 seconds a namespace by default, and a read that runs out stops the write for a person. By default an in-patient movement on another visit shows on the plan beside the resend and doesn't stop it, as do an emergency or out-patient movement (class E or O) and a pre-admission on file before the case; a cancel, merge or discharge on the case's own visit, or a change to the record, still stops it. A site that wants another visit's movement to stop the write for a person sets one value in the site profile's JSON, `"further_messages": {"in_patient_movement": "stop"}`, as 1.1.0 and 1.1.1 did, and the demo keeps that stop. It can't see a change made by hand at the receiver, and nothing holds the feed during a correction. A person who reinvestigates a stopped case meets the same stop until they close it by hand. 1.1.1's stop held a right resend in the held-out case F07 ([release 1.1.x](https://github.com/MxSalata/shutter/blob/main/docs/readme/fair-test.md#release-11x)). | `further_messages.scan_seconds` in the site profile sets the read's time; `further_messages.in_patient_movement: stop` brings the stop back. | By design; `show` is the default since 1.2.0 |
| **Restriction fields aren't read, and a death is read from one message** | A failed message's own PID-29 or PID-30 sends the case to a person (Rules only aside). A death on an earlier message of the patient's, or an N after a Y, isn't compared, and a message that concerns a restricted record isn't stopped for that reason. | | Open |
| **The operation travels, not the message** | A write carries fixed fields only, with no demographics. A resent A08 is an update with no location: only the record's version moves, so it can't recover a ward or bed move. The location check in the next row holds it instead. | | By design |
| **A site's own message meanings** | Shutter reads messages the standard way: A02 is a move, and an A08 is an update that moves nothing. Systems differ, and may differ between sites on one product. Where an A08 names another ward or bed than the receiver holds, the gate blocks a resend or a closure (`UPDATE_LOCATION_DIFFERS`) for a person, unless `further_messages.a08_location` is `show`; showing it removes the stop and recovers nothing. Consultant and specialty changes aren't carried. | Confirm trigger meanings, location fields, identifiers and times for a feed before recovery is enabled there; an approval doesn't stand in for that. | Open |
| **Verified is narrow** | It belongs to case recovery through the receiver's API, and means the receiver's receipt and history held this operation's key, with the digest, ward and bed they name, when they were read. An outage's resend is not verified in this sense: a message reads completed when the engine's new header reads Completed, which proves what the entry's `ack_level` declares, or closed as already delivered on the receiver's declared duplicate answer. A receipt that names none has nothing to compare, a receiver whose site profile entry says `strict_answers: false` isn't compared, and a closed case isn't read again. | | By design |
| **Times are taken as stated** | Two sources count as simultaneous within the site's `feed.source_skew_seconds` (300 by default), in a receiver that keeps history; past that they are ordered by event time. A sender's clock running ahead by more than five minutes is caught against the engine's receive time. One running behind isn't noticed, since a queue looks the same. Two source systems' movements within five minutes go to the board or a person, so a site with two sources may see this often. | The site profile holds one time zone, so senders that give no offset must share it. | By design |
| **The receiver's API is trusted, within limits** | A receiver that ignores the condition on a write, or a read that returns only part of the history, isn't detected. A gateway's sign-in page, or a 200 with no receipt, reads as not the receiver's answer and goes to a person. A rehearsal relies on the receiver honouring `dry_run`: one that declares it and writes anyway has taken the write before any release, and Shutter raises an alert, records it and stops the case for a person, but cannot undo it. | Keep the answer check on and compare the receiver's answers with the contract on a test endpoint. `strict_answers: false` reads answers on their status alone and skips the receipt comparison before a reconcile. | Open |
| **The alert route reads little** | It takes the alert's words and the message the alerting item was sent. A session that sends one item several different messages gets an alert naming them and no case, since an alert doesn't say which one failed. Words it doesn't know read as an uncertain outcome and go to a person, and a resend made by hand in the Message Viewer isn't seen. A forward nobody answers is tried again for five minutes by default, so a failure during a longer downtime still becomes no case ([the install guide, section 10](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md#10-what-a-watched-namespace-does-not-get)). | Keep approval on for that route. | By design |
| **Identifiers** | The visit number is read from PV1-19.1 without its assigning authority and addresses the receiver alone; a clash blocks for a person. Shutter reads standard HL7 positions whatever a site's schema says (MSH-3, PID-3, PV1-3, PV1-19, EVN-6). MSH-4 isn't read. An identifier that appears only in a receiver's or engine's free text can reach the model. Another patient's message under the same visit number can't close a case; a patient's later message under a new identifier, after a merge the receiver hasn't taken, isn't counted either. | The visit number must be unique at the receiver across every feed; a site that moves those positions must not enable recovery; MSH-3.1 must name one system. | Open |
| **Overtaken isn't compared** | A closure can also verify when the receiver's history shows no later event and only the feed sent one, whose delivery failed: that later message's own case then recovers the patient, and until it does the receiver is behind. When a later transfer closes a failed transfer, wards aren't compared. A hand entry the receiver records as an update, or times before the failed event, can see the resend proposed again. | | Open |
| **Admissions and cancels** | Same-minute moves from a source without seconds share an operation key, and the second stops for a person. An admission on a 404 inside an incident is held for a person too: it joins the incident's one approval, and the task asks the approver to check the receiver's own screen. | | By design |
| **The forwarder's sign-in can open cases** | An automatic release checks that the named namespace holds the message posted and that its session went to that receiver, so an invented movement goes to a person. A genuine message posted again passes that check. | Give that password an integration credential's care; a site whose forwarder is on another instance has to turn the check off ([the install guide, section 3.5](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md#3-shape-a-shutter-in-its-own-namespace)). | By design |
| **One instance** | Failover, mirrors and restoring from a backup aren't tested. Grouping cases into an incident takes no lock per receiver. | Keep Case Workflow's pool at one. | Untested |
| **Shutter's own stop covers its recovery calls only** | **Stop Shutter recovery** on the Settings page refuses every recovery call Shutter makes, from the moment it commits; a call admitted before it may still complete, and an outage's resend halts before its next message, and it holds neither the hospital's feed nor anything else that writes to a receiver ([the stop](https://github.com/MxSalata/shutter/blob/main/docs/CONTRACTS.md#18-shadow-mode-and-the-recovery-stop-v150)). IRIS's own stop works too: [below](#stopping-every-write). The case page doesn't show that the item is off. | Stop Shutter recovery for Shutter's writes; disable each connector item that writes to a receiver to hold everything through it. | IRIS's stop tested on build 109, 8 November 2026 |
| **Onboarding edits the watched production** | It renames the site's Ens.Alert, adds two items and maps Shutter's classes, and the production then needs Shutter's database to start ([the install guide, section 10](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md#10-what-a-watched-namespace-does-not-get)). | Try it first on captured traffic in a sandbox, with a separate read-only evaluation, not between a live production's alerts and their consumer ([pilot it first](https://github.com/MxSalata/shutter/blob/main/docs/readme/first-steps.md#pilot-it-first)). | By design |
| **No local-model profile** | On purpose: the board works through typed tool calls, which a frontier model makes reliably on evidence this detailed. A site's own model behind an API would be a provider in the Config Store; that is untested, though another hosted provider was: OpenAI's `gpt-4.1`, by hand, ran S2 and S8 as expected twice on build 109, unpriced and outside the day's budget ([another-provider.md](https://github.com/MxSalata/shutter/blob/main/docs/readme/another-provider.md)). | | By design; a site's own model is untested |
| **The install configures Anthropic only** | Another provider is set by hand in the Config Store and on the board items. Its runs are unpriced on the Costs page and outside the day's budget, and OpenAI's newer models refuse the runner's `max_tokens` (AI Hub [#24](https://github.com/intersystems-community/ai-hub-eap-bugreports/issues/24)), so the test ran on `gpt-4.1`. | [Running the board on another provider, by hand](https://github.com/MxSalata/shutter/blob/main/docs/readme/another-provider.md). | Tested by hand on build 109, 8 November 2026 |
| **The evaluation** | One recording per board member and case, with one model, and the catalogue was written alongside these scenarios. Each agent is given the catalogue's matching entry and preferred outcome; the coordinator took that outcome in 24 of 25 recorded plans, S8 included, and in S22 Records Out the alternative the matcher had already chosen from the site's policy: agents applying written policy and keeping dissent, not answering unaided. Conformance is told to judge the message alone, so its resend on a valid message is expected: it is in 11 of the 13 dissenting passes; in S25, on a message that does not parse, conformance escalates and the plan resends; another specialist dissents in 3. [Three earlier batches](https://github.com/MxSalata/shutter/blob/main/docs/readme/evaluation.md#not-yet-measured), on earlier versions, kept the coordinator's disposition in all 14 plans: stable given the catalogue, not a controlled repeat. The injected instruction (S4) now reaches the agents only as a flag; [its text was sent once](https://github.com/MxSalata/shutter/blob/9dfd675438022cb1ae4c8a9a35ef6fc9673def27/fixtures/records/scenario-S4-coordinator-1.json), a weak test, since S4's right answer is a resend. | Twelve sealed held-out cases were played since, three runs each: [fair-test.md](https://github.com/MxSalata/shutter/blob/main/docs/readme/fair-test.md). | Measured |
| **Spend** | A storm of one kind convenes one board, which the other cases with its failure signature follow, each through its own gate and approval. `SHUTTER_DAILY_BUDGET_USD` admits a new live run only when the day's recorded spend, the reservations for the runs in flight and the new run's own estimate (by default the mean of the last twenty live runs, else 0.50 USD) fit within it, and a user's share the same way; the check and the reservation are one locked step, so runs that start in the same moment, a board's three specialists for one, cannot each be admitted on the same remaining allowance. A run that does not fit is refused, after which a case the catalogue gives to the board or a person goes to a person with no plan, and others take the rules path ([more](https://github.com/MxSalata/shutter/blob/main/docs/readme/running.md#more-about-running-it)). That bounds estimates, not the bill: a run can cost more than its estimate, a reservation older than 20 minutes is released whether or not its run has ended, a run's cost counts nowhere for the moment between its end and its row being written, and a production review's cost is kept on the review, which the day's spend does not read. The SQL diagnostic `TestRun` goes through the same admission and its cost is counted ([ai-hub.md](https://github.com/MxSalata/shutter/blob/main/docs/readme/ai-hub.md#the-sql-diagnostic-outside-the-live-role)). The online demo's instance resets every hour; its live spend is capped at 5 USD an hour, 2 USD of it for the judges' account, which all judges share, and 15 USD a day. | Keep a hard limit at the provider. | By design |

## Stopping every write

Shutter's own switch, **Stop Shutter recovery** on the Settings page (an operator or an approver, with a reason), refuses every recovery call Shutter makes until an approver clears it, and a plan made before the stop or the clear can't be written, so the case needs fresh evidence and a new plan. An outage's resend can't be approved while it is set, and a resend under way halts before its next message: its rest go only by a new approval once the stop is cleared. Already handled by hand sends nothing, so it stays open to a person ([the stop](https://github.com/MxSalata/shutter/blob/main/docs/CONTRACTS.md#18-shadow-mode-and-the-recovery-stop-v150)). It doesn't hold the hospital's feed. IRIS's own stop holds everything through a connector item: disable each connector item that writes to a receiver (Downstream Out, and Records Out for the second receiver) in Interoperability > Configure > Production (select the item, clear Enabled, Apply), or `Do ##class(Ens.Director).EnableConfigItem("Downstream Out", 0, 1)`. What is sent to it waits in its queue and runs when it is enabled again; Shutter reads the receiver again before any write.

Tested on 8 November 2026 on build `2027.1.0AI.109.0`: with the connector item Downstream Out disabled, an approved S2 waited at "approved", its preflight read held in the item's queue, and nothing reached the receiver. We then moved the patient at the receiver directly; on re-enabling, the read found the new version, the gate voided the approval, and the case was planned afresh and closed as superseded, with nothing written. With no change in between, the held resend went through and was verified. The case page doesn't show that the item is off. Records Out wasn't part of the test.
