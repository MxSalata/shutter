# Limits, plainly

For a clinical safety officer: [the hazards, data flow, threats and what a site still owes](https://github.com/MxSalata/shutter/blob/main/docs/SAFETY.md).

Every limit the README's "Limits, plainly" names, in full, word for word. The README states the ones that matter most and sums up the rest in its last bullets; each of these is named there, and some carry more detail here. Scenarios: [scenarios.md](https://github.com/MxSalata/shutter/blob/main/docs/readme/scenarios.md); what each row of "What can go wrong when you resend" doesn't cover: [edge-cases.md](https://github.com/MxSalata/shutter/blob/main/docs/edge-cases.md); limits of a running instance: [running.md](https://github.com/MxSalata/shutter/blob/main/docs/readme/running.md#other-limits).

- How many of a hospital's failures Shutter resolves has not been measured: the scenarios are written by us and the data is synthetic, and until a receiver is given an API, help means a case and a drafted email.
- Orders, results and documents up to 2 MB get a case and a drafted email, never a resend; larger gets an alert and no case.
- Without an API key the agents replay recorded runs. A case with no recording, such as one from your own HL7 file, takes the rules path: the gate alone decides and a resend waits for a person.
- The receiver is a demo bed-management system built for the scenarios. Shutter resends only to a receiver whose API (state, receipt, capabilities and operations paths) the site profile describes. A plain MLLP receiver gets no resend, because an ACK says a message arrived, not what the receiver now holds: a NACK or a lost connection on a stock `EnsLib.HL7.Operation.TCPOperation` with `AlertOnError` on opens a case through the alert intake, and a person gets the evidence and the reason nothing was sent (`tests/e2e/plain_receiver_check.py`).
- A message accepted by a transport ACK and then lost downstream raises nothing in Shutter: on stock settings a commit ACK completes exactly as an application ACK does, which we measured ([the install guide, section 9](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md#9-onboarding-several-namespaces)).
- A write whose answer was lost is judged at the last read, about 70 s after the attempt by default: with no sign of it by then, the case says not committed and a person decides. A slower receiver can still commit it; a site with one raises `UncertainSettleSeconds`.
- An operation that retries for ever (`FailureTimeout` -1) at a receiver that also has an API: a resend writes through the API, approved or, at a tier the site's policy releases (the shipped setting for tiers 1 and 2), with no approval, and the engine then delivers the same message itself when the listener returns (measured on 109, by the approved route). Keep `FailureTimeout` 0 on such a receiver.
- **One visit at a time.** A failed message is compared with its own visit at the receiver. Shutter doesn't see the patient's other visits, merged records or linked numbers, and a withheld merge holds nothing else back.
- **Death and restriction fields aren't read.** A message that carries or clears a death, or concerns a restricted record, isn't stopped for that reason.
- **The operation travels, not the message.** A write carries fixed fields only, with no demographics. A failed A08 isn't recovered: only the record's version moves.
- **A site's own message meanings.** Shutter reads messages the standard way: A02 is a move, and an A08 is an update that moves nothing. Systems differ, and may differ between sites on one product. Where an A08 carries a bed or ward move, a failed one isn't recovered, and Shutter doesn't count a later one as a move, so an older movement can look current. Consultant and specialty changes aren't carried. Trigger meanings, location fields, identifiers and times must be confirmed for a feed before recovery is enabled there, and an approval doesn't stand in for that.
- **Verified is narrow.** It means the receiver's receipt and history held this operation's key when they were read. Ward and bed aren't compared, and a closed case isn't read again. A corrected message under a key already committed (same source, patient, encounter, event and event time) can close as already applied, and a receipt lookup that errors at that last step can read as no receipt. To be fixed in v1.1.0.
- **A receiver with no history** can still be written to: a move another system made outside the feed isn't seen, the resend goes over it, and verification then fails and asks a person. To be fixed in v1.1.0.
- **Times are taken as stated.** Two sources count as simultaneous only at the same recorded second, in a receiver that keeps history: a move a second earlier from another system is ordered by event time, and the later one is resent, with no person at a tier the site's policy releases. A sender's clock running behind isn't noticed, and the clock-change stop applies only to Europe/London. To be fixed in v1.1.0. The site profile holds one time zone, so senders that give no offset must share it.
- **The receiver's API is trusted.** A receiver that ignores the condition on a write, a gateway's sign-in page answering in its place, a read that returns only part of the history, or a 200 saying a message was already committed on its first delivery, isn't detected (that last one counts as delivered and opens no case). A rehearsal relies on the receiver honouring `dry_run`: one that declares it and writes anyway has taken the write before any release, and Shutter raises an alert and records it, but cannot undo it.
- **The alert route reads little.** It takes the alert's words and the session's first HL7 message. A process that sends several messages to one receiver gets a case for the first failure only, with a DTL on the route the case holds what the service received, not what the operation sent, and alert wording it doesn't know or a resend made by hand in the Message Viewer can mislead the case, so keep approval on for that route. A forward is never retried, so a failure during Shutter's downtime becomes no case ([the install guide, section 10](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md#10-what-a-watched-namespace-does-not-get)).
- **When no agent can answer** (no key, the budget spent, the provider refusing), a case the catalogue gives to the board falls back to the rules path, S8's included: it reads as a plain resend, and a person must still approve it. To be fixed in v1.1.0.
- **Incidents.** An item's next version can come from the encounter as read at verification, not from the previous item's receipt, and an arriving patient's chain released before the occupant's can wait on it with no time limit. To be fixed in v1.1.0.
- **An incident stops at about four chains under one approval.** The shared approval task lists every chain in a Workflow message of 2,000 characters. Measured on v1.0.0: 8 failures in 4 chains are approved and released; 10, 40, 200 and 1,000 are taken in and grouped into one incident within 70 s, and the incident then abandons itself: no task, nothing written, no case lost, and every case closes `failed` for a person to handle one by one. To be fixed in v1.1.0 ([the measurements](https://github.com/MxSalata/shutter/blob/main/docs/readme/storm-at-scale.md)).
- **Identifiers.** The visit number is read from PV1-19.1 without its assigning authority and addresses the receiver alone, so it must be unique at the receiver across every feed; a clash blocks for a person. Shutter reads standard HL7 positions whatever a site's schema says (MSH-3, PID-3, PV1-3, PV1-19, EVN-6), so a site that moves these must not enable recovery. MSH-3.1 must name one system, as MSH-4 isn't read. An identifier that appears only in a receiver's or engine's free text can reach the model.
- **Overtaken isn't compared.** A closure can also verify when the receiver's history shows no later event and only the feed sent one, whose delivery failed: that later message's own case then recovers the patient, and until it does the receiver is behind. Wards aren't compared, so a failed update or discharge followed by a later transfer closes as superseded at a current-state receiver, and the patient can stay undischarged there. A hand entry the receiver records as an update, or times before the failed event, can see the resend proposed again. To be fixed in v1.1.0.
- **Admissions and cancels.** A failed admission and a failed discharge can resend the admission to a closed unit, and a failed admission with no record at the receiver can make a second record for a patient entered by hand. Same-minute moves from a source without seconds share an operation key. To be fixed in v1.1.0.
- **The forwarder's sign-in is trusted,** and what it posts is not looked up: at a tier that releases by policy, an invented movement from that sign-in could write with no approval ([the install guide, section 3.5](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md#3-shape-a-shutter-in-its-own-namespace)).
- **One instance.** Failover, mirrors and restoring from a backup aren't tested, and there is no switch yet to stop all writes. Keep Case Workflow's pool at one: grouping cases into an incident takes no lock per receiver.
- **Onboarding edits the watched production.** It renames the site's Ens.Alert, adds two items and maps Shutter's classes, and the production then needs Shutter's database to start ([the install guide, section 10](https://github.com/MxSalata/shutter/blob/main/docs/INSTALL.md#10-what-a-watched-namespace-does-not-get)). Try it first on captured traffic in a sandbox, with a separate read-only evaluation, not between a live production's alerts and their consumer.
- No local-model profile, on purpose: the board works through typed tool calls, which a frontier model makes reliably on evidence this detailed. A site's own model behind an API would be a provider in the Config Store; that is untested.
- The evaluation is one recording per board member and case, with one model, and the catalogue was written alongside these scenarios. Each agent is given the catalogue's matching entry and preferred outcome; the coordinator took that outcome in 24 of 25 recorded plans, S8 included, and in S22 Records Out the alternative the matcher had already chosen from the site's policy: agents applying written policy and keeping dissent, not answering unaided. Conformance is told to judge the message alone, so its resend on a valid message is expected: it is in 11 of the 13 dissenting passes; in S25, on a message that does not parse, conformance escalates and the plan resends; another specialist dissents in 3. [Three earlier batches](https://github.com/MxSalata/shutter/blob/main/docs/readme/evaluation.md#not-yet-measured), on earlier versions, kept the coordinator's disposition in all 14 plans: stable given the catalogue, not a controlled repeat. The injected instruction (S4) now reaches the agents only as a flag; [its text was sent once](https://github.com/MxSalata/shutter/blob/9dfd675438022cb1ae4c8a9a35ef6fc9673def27/fixtures/records/scenario-S4-coordinator-1.json), a weak test, since S4's right answer is a resend.
- Spend: a storm of one kind convenes one board, which the other cases with its failure signature follow, each through its own gate and approval; `SHUTTER_DAILY_BUDGET_USD` stops new live runs once the day's recorded spend and reservations reach it, after which cases take the rules path; runs in flight can finish past it, so keep a hard limit at the provider ([more](https://github.com/MxSalata/shutter/blob/main/docs/readme/running.md#more-about-running-it)). The online demo's instance resets every hour; its live spend is capped at 5 USD an hour, 2 USD of it per judge, and 15 USD a day.
