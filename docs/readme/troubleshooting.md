# Troubleshooting

Troubleshooting, in full (the README links it from Try it). The health report is `curl http://localhost:52773/api/shutter/health`; more about running Shutter: [running.md](https://github.com/MxSalata/shutter/blob/main/docs/readme/running.md).

- **`install.sh` stops at a check.** It prints `[fix]` with what to do for each one, and changes nothing until every check passes. A port in use: `SHUTTER_WEB_PORT` is the web app's, `SHUTTER_SUPERSERVER_PORT` is 1972, IRIS's own; with no `.env` yet, `SHUTTER_SUPERSERVER_PORT=1973 ./install.sh --replay` keeps it in the `.env` it creates, and otherwise set it in `.env`.
- **Not healthy after 25 minutes.** `install.sh` prints the last 30 lines of the log and the health address; `curl http://localhost:52773/api/shutter/health` is the report to read.
- **The Doctor.** In the Management Portal's SQL page (namespace `SHUTTER`, as `_SYSTEM`), `SELECT Shutter.Setup_Doctor()`: `missing_items` and `disabled_items` should be `[]`, `production_state` `running`, `board_members` 5 (the board's four and the single investigator), `recordings` more than 0 (174 on build 109: every recording, not only the board's 100 runs) and `second_parser` `probe: ok` ([the values on build 109](https://github.com/MxSalata/shutter/blob/main/docs/readme/receipt-109.md)).
- **"License limit exceeded" or "Service Unavailable".** The Community licence's connections are used up, usually by repeated sign-ins: about eight on build 154. Since 1.2.0 signing out frees its connection at once; a tab closed without signing out holds one for 15 minutes (2 minutes on the public demo, `SHUTTER_DEMO_PORTAL=1`). The web app carries on, but new Management Portal sessions and terminals are refused. The public demo can still lock: 8 or more sign-ins within 2 minutes without signing out (visitors arriving close together, or tabs closed while signed in) refuse the portal until 2 minutes after the last of them. Wait about 2 minutes, or restart the container (`docker compose restart`), which frees them at once.
- **A case says the production restarted, a case stays in a working state, or a press got no answer.** [continuity.md](https://github.com/MxSalata/shutter/blob/main/docs/readme/continuity.md) says what a restart, a lost answer or an upgrade keeps, what it marks, and what a person does next.
- **On the first start,** `ERROR #5002 ... Sharding` and "Error trading CSP licenses" come from the IRIS image and are harmless.
- **`install.sh` says the AI Hub image is too small.** The load was cut short; load the file again (a complete load is about 5.4 GB of content, from the 5.5 GB file).
- **A task the web app says is not now.** Settings, Your tasks, says for each task whether it is ready for you here, what stands in the way and the next step, from what the app already reads (your sign-in's `can` in `GET /me`, `GET /settings`, `GET /recovery-control`, the site profile, `GET /health`'s `last_live_run`, `GET /costs`). It is read only: each page checks again when you press. What each task needs:

  | Task | Needs | Not now when | Next step |
  | --- | --- | --- | --- |
  | Read cases and recorded runs | A sign-in | | |
  | Run a scenario | `Shutter_Scenarios`, on a demo installation | It is a site's installation (`demo=0`) | Play them in the trial (Help, Open the trial environment). Without `Shutter_LiveAgents` or a model key the runs replay the recordings and spend nothing |
  | Ask the agents a question of your own | `Shutter_Operate` and `Shutter_LiveAgents`, a model key | No key; the replay edition; the API mimic on (a test fixture, on a demo only); the day's budget or your share of it spent; the provider refusing the key | Set `ANTHROPIC_API_KEY` (or `OPENAI_API_KEY`) in `.env` and start the production again; switch to the AI Hub edition; wait for the reset or raise `SHUTTER_DAILY_BUDGET_USD`; switch the mimic off (`Shutter.Mock.Setup_Disable`); wait, then check the key with the provider. A suggested question still answers from its recording |
  | Approve a recovery or an incident's release | `Shutter_Approve`, recovery enabled and not stopped ([CONTRACTS 18](https://github.com/MxSalata/shutter/blob/main/docs/CONTRACTS.md#18-shadow-mode-and-the-recovery-stop-v150)) | Shadow mode; the stop; a control that cannot be read | Set `recovery.mode` to `enabled` in the site profile, once the site has decided; a person with `Shutter_Configure` and `Shutter_Approve` clears the stop with a reason. A plan made before either needs fresh evidence |
  | Escalate a case by email | `Shutter_Operate` | Only without `Shutter_Operate`; in shadow mode it is ready with a limit: it is recorded and reads Not sent | Enable recovery, or allow email in shadow mode (`notifications.shadow_delivery`), and send it again |
  | Close a case handled by hand | `Shutter_Operate`, and `Shutter_Approve` as well under the two-person rule (`approvers.close_needs_approver`) | Without `Shutter_Operate`; the site keeps the two-person rule and you are not an approver | Ask an approver |

  Each fact is marked Set up (what the installation is configured to do), Now (what held when the page read it, with that time in the feed's zone, and in UTC in its tooltip and in Technical) or Seen (the newest run for a real model, never the API mimic, with when it started and whether it answered or was refused before any call to it, for the day's budget or the provider refusing the key, from `GET /health`'s `last_live_run`, its status as the store keeps it in Technical; until the health report answers, and on an answer without it, the costs' count of the board's runs that reached a model).
