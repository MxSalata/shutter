# Safety: what can go wrong, what stands against it, and what a site still owes

**Releases 1.1.1 and 1.1.2: what changed since 1.0.0.** The rest of this page describes release 1.0.0, with every link pinned to that tag; the lines below are pinned to `v1.1.1` or `v1.1.2`, and [the change log](https://github.com/MxSalata/shutter/blob/v1.1.2/CHANGELOG.md) has the rest.

- **A person approves every resend by default.** The shipped site profile asks for approval at every tier, and the board for interleaved chains ([Store/SiteProfile.cls:47-51](https://github.com/MxSalata/shutter/blob/v1.1.1/src/Shutter/Store/SiteProfile.cls#L47-L51)). A demo install keeps the 1.0.0 table as its own, labelled setting ([:55-60](https://github.com/MxSalata/shutter/blob/v1.1.1/src/Shutter/Store/SiteProfile.cls#L55-L60)). This changes "Some writes had no person at all" and "A write with no person" below.
- **No write while the engine still has the message.** At a stock HL7 TCP operation the case waits while the engine is trying (`ENGINE_STILL_TRYING`), closes when the engine delivers, and goes to a person when the receiver may already hold it ([Process/CaseWorkflow.cls:1180](https://github.com/MxSalata/shutter/blob/v1.1.1/src/Shutter/Process/CaseWorkflow.cls#L1180)). This changes "The engine delivers it too" below.
- **A movement on another visit shows on the plan, and stops the write only where the site profile says so** (1.1.2). By default a further in-patient movement for the patient on another visit goes on the plan beside the resend ([Store/SiteProfile.cls](https://github.com/MxSalata/shutter/blob/v1.1.2/src/Shutter/Store/SiteProfile.cls)). `"further_messages": {"in_patient_movement": "stop"}` in the site profile's JSON brings back the stop of 1.1.0 and 1.1.1 (`FURTHER_MOVEMENT`, [Operation/Gate.cls](https://github.com/MxSalata/shutter/blob/v1.1.2/src/Shutter/Operation/Gate.cls)); a fresh demo install keeps it ([Setup.cls](https://github.com/MxSalata/shutter/blob/v1.1.2/src/Shutter/Setup.cls), `DemoProfilePolicy`). **Not yet in 1.1.2:** nobody reads a shown movement at a tier released by policy, or under an incident's shared approval, whose task leaves it out; one that arrives after the approval passes the write unseen, where 1.1.1 stopped it; and a demo whose profile a person or the onboarding saved reads `show` after the upgrade. A site that uses incidents or releases a tier by policy should set `stop` before it upgrades.
- **A receiver's outage is one incident** for a receiver with a `watch` block, read from the engine with no connection to the receiver ([Production.cls:118](https://github.com/MxSalata/shutter/blob/v1.1.1/src/Shutter/Production.cls#L118)). Nothing tells anyone it opened: the site's own alert must carry the link.
- **A receipt that differs stops the close.** A receipt under the failed key with other content goes to a person (`RECEIPT_PAYLOAD_DIFFERS`, [Operation/Gate.cls:186](https://github.com/MxSalata/shutter/blob/v1.1.1/src/Shutter/Operation/Gate.cls#L186)). On 1.1.1 it also stopped a receipt whose bed is JSON null ([Operation/Verify.cls:337](https://github.com/MxSalata/shutter/blob/v1.1.1/src/Shutter/Operation/Verify.cls#L337)): safe, as nothing is written, but a person got a case the receipt had settled (held-out case F03). 1.1.2 reads a bed that is null, missing or empty as saying nothing about the bed ([Operation/Verify.cls](https://github.com/MxSalata/shutter/blob/v1.1.2/src/Shutter/Operation/Verify.cls), `BedStated`); with that check loaded over 1.1.1's code, the board's reconcile closed F03 in all three runs ([release 1.1.x](https://github.com/MxSalata/shutter/blob/main/docs/readme/fair-test.md#release-11x)).
- **An incident of any size is approved once** (1.1.2), by one task that binds every chain, where 1.1.1 abandoned one above about four chains and sent every case to a person ([docs/readme/storm-at-scale.md](https://github.com/MxSalata/shutter/blob/v1.1.2/docs/readme/storm-at-scale.md)).
- **1.1.1 itself** fixes what the agents read: the route item keeps the receiver's capability profile, so the live board no longer holds every resend for more evidence ([Util/ModelView.cls](https://github.com/MxSalata/shutter/blob/v1.1.1/src/Shutter/Util/ModelView.cls)). On the held-out cases its board proposes what 1.0.0's did in all 36 runs.

This page is for a site's clinical safety officer or information governance lead who has never seen Shutter. It lists hazards to patients, where patient data goes, who can do what, and what the site must do itself. Each row names the code behind it, so you can check it.

**This is not a clinical safety case.** No standard has been applied to Shutter and none is claimed as met. No regulatory classification has been made: that depends on a site's intended use, and the site's clinical safety officer assesses it. A site's own clinical safety case is the site's. See [What a site still owes](#what-a-site-still-owes).

Below the 1.1.1 and 1.1.2 lines above, it describes release 1.0.0: every repository link opens a file at the tag `v1.0.0`, so its line numbers remain fixed when later releases are published. A later release may differ from what this page describes. Code paths are shown under `src/Shutter/` unless they start otherwise; each is a link.

## What Shutter does, in brief

When an HL7 delivery from an IRIS production fails, Shutter opens a **case** and gathers evidence: the message, and what the **receiver** (the system the message was going to) now holds. A **board** of AI agents may propose a plan; with no agents, rules do. A deterministic **gate** then decides whether anything may be written. A write is one conditional write through the receiver's API, after which Shutter reads the receiver's receipt and history for it. A receiver without such an API, such as one using only the Minimal Lower Layer Protocol (MLLP) for HL7 transport, never receives a resend from Shutter. A person receives the evidence and a drafted email ([README.md:304](https://github.com/MxSalata/shutter/blob/v1.0.0/README.md?plain=1#L304)).

Each receiver has a **tier** in the **site profile**, and the profile's `policy` says, by tier and by the shape of the failure, whether a write needs an **approver** or goes with no person.

## Read this first

- **A default install is the demo, with documented passwords.** `demo` defaults to 1, and `operator`, `approver` and `forwarder` then sign in with `shutter` unless a password is set ([Setup.cls:110](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L110), [:310-312](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L310-L312), [docs/INSTALL.md:40](https://github.com/MxSalata/shutter/blob/v1.0.0/docs/INSTALL.md?plain=1#L40), [docs/CONTRACTS.md:1248](https://github.com/MxSalata/shutter/blob/v1.0.0/docs/CONTRACTS.md?plain=1#L1248)). For anything but a trial, install with `-Ddemo=0`.
- **Some writes had no person at all, as 1.0.0 shipped.** Tiers 1 and 2 write a single failed message with `automatic` policy, and tier 1 an ordered chain too ([Store/SiteProfile.cls:32](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Store/SiteProfile.cls#L32)). A profile entry with an API but no `tier` is treated as tier 2 ([Store/SiteProfile.cls:412](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Store/SiteProfile.cls#L412)). A receiver the profile doesn't name gets no resend on a site install ([docs/INSTALL.md:163](https://github.com/MxSalata/shutter/blob/v1.0.0/docs/INSTALL.md?plain=1#L163)). Giving a receiver an API at those tiers is what allows it ([docs/INSTALL.md:478-482](https://github.com/MxSalata/shutter/blob/v1.0.0/docs/INSTALL.md?plain=1#L478-L482)). A site decides this table before any receiver gets an API. In 1.1.0 the shipped profile asks a person at every tier (approval for single and ordered chains at tiers 1 to 3, the board for interleaved ones), and a demo install keeps the 1.0.0 table as the demo's own, labelled setting.
- **After 24 hours with no decision, nobody is told.** The approval task is cancelled and the case moves to `escalated` ([Process/CaseWorkflow.cls:1425-1433](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Process/CaseWorkflow.cls#L1425-L1433)). No mail or alert goes out by itself. Someone has to be watching.
- **There is no switch to stop every write** ([README.md:321](https://github.com/MxSalata/shutter/blob/v1.0.0/README.md?plain=1#L321)).
- **Every proof here was played against the demo receiver or a stub listener** ([docs/edge-cases.md:5](https://github.com/MxSalata/shutter/blob/v1.0.0/docs/edge-cases.md?plain=1#L5)). What a real receiver does is for its interface specification and the site's testing to say.
- **With live agents on, pseudonymised case data goes to an outside model provider.** With no provider configured (an instance never given a key), recorded runs are replayed and nothing goes to any model. A provider once configured stays configured when the key leaves the environment ([Setup.cls:2121](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L2121)), and the agents set to `auto` then run live ([Bridge/Operation/Agent.cls:80](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Bridge/Operation/Agent.cls#L80)): `SELECT Shutter.Setup_RecordAgentMode('replay')` pins them to replay ([Setup.cls:2278](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L2278)).
- **The forwarder's sign-in is trusted.** What it posts isn't looked up, and at a tier that releases by policy it can cause a write with no person ([README.md:320](https://github.com/MxSalata/shutter/blob/v1.0.0/README.md?plain=1#L320), [docs/INSTALL.md:166-170](https://github.com/MxSalata/shutter/blob/v1.0.0/docs/INSTALL.md?plain=1#L166-L170)).

## How to read the proof columns

| Label | Means |
| --- | --- |
| **CI** | A test or scenario the repository's CI runs on IRIS for Health Community 2026.2, with agents replaying recorded runs and the gate, rules and demo receiver running for real |
| **Script** | A test in the tree that isn't a CI step, run by hand or from an install check |
| **Measured** | A one-off result the README or install guide reports, on the build it names |
| **Ran** | Run at this release for this page |
| **Read** | Read in the code only. Nothing was played for that row |

The CI tests and scenarios were not rerun for this page. They are cited so that readers can run them. ### What reaches a model

- **Kept:** each listed data structure has a keep list specifying which fields to retain ([Util/ModelView.cls:21-56](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L21-L56)). For data structures without a keep list, all fields are retained except those with denied keys ([Util/ModelView.cls:170](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L170)).
- **Denied by the reduction:** name parts, birth date, sex, address, phone, email, next of kin, religion, ethnicity, marital status, nationality, language, national ids and the headline ([Util/ModelView.cls:19](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L19), [:129](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L129)).
- **Identifiers become tokens:** every PID-3 repetition, PID-5 name parts, PID-7, MRG ids and names, id keys and operation-key pieces ([Util/ModelView.cls:65](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L65), [:266-306](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L266-L306), [:318-346](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L318-L346)). The map is kept inside IRIS ([Store/CaseToken.cls:1-4](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Store/CaseToken.cls#L1-L4)).
- **Fail closed:** if the case's own patient or encounter has no token, or the message can't be read, no request is built and the case escalates ([Util/ModelView.cls:79-82](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L79-L82), [:261](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L261), [:264](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L264), [Process/CaseWorkflow.cls:714](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Process/CaseWorkflow.cls#L714), [:718-721](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Process/CaseWorkflow.cls#L718-L721), [:765-770](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Process/CaseWorkflow.cls#L765-L770)). This covers the case's own patient and encounter only.
- **Notes:** become flags. The text goes only if the site sets `model_content.free_text` true, tokenised and cut at 500 characters ([Util/ModelView.cls:176-197](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L176-L197), [:189-190](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L189-L190), [Store/SiteProfile.cls:35](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Store/SiteProfile.cls#L35)). The case records this for a board ([Process/CaseWorkflow.cls:663-666](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Process/CaseWorkflow.cls#L663-L666)), but not for a question or a publisher read.
- **Outside strings:** `text`, `error`, `message` and `detail` are cut at 1000 characters and flagged when they read like an instruction, and are still sent ([Util/ModelView.cls:62](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L62), [:139-142](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L139-L142)). Other kept strings go uncapped and unflagged. Only this case's identifiers are replaced, so another patient named in an error's text is not.
- **Left untokenised:** case and scenario ids; ward, bed and location codes; event, admit, applied and observed times; source system; facility and application codes; control ids; IRIS header and session ids; namespace, production and route names; patient class; HTTP statuses; observation ids and value types; digests. A bed conflict can carry another patient's encounter, as a token, with its state, ward and bed ([Util/BedConflict.cls:32-42](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/BedConflict.cls#L32-L42)).
- **Known gaps:** an identifier under three characters is neither tokenised nor refused ([Store/CaseToken.cls:57](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Store/CaseToken.cls#L57)). A birth date in any form but HL7 or ISO isn't replaced ([Util/ModelView.cls:281-284](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Util/ModelView.cls#L281-L284)). With free text on, a relative or clinician named in a note goes as written, as does a nickname or misspelling.
- **The repository does not establish how model requests are transported.** The provider is reached by AI Hub's library, from a configuration of provider, model and key ([Bridge/Runner/AIHub.cls:149-156](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Bridge/Runner/AIHub.cls#L149-L156)). Shutter sets no endpoint, proxy or TLS option for it. Endpoint, TLS verification, proxy handling and what the provider retains, prompt cache included ([Bridge/Runner/AIHub.cls:100](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Bridge/Runner/AIHub.cls#L100)), are for the vendor and the provider's terms.

Whether the tokenised copy is personal data under UK GDPR is for the site to assess. Timestamps, ward codes and a stable per-case token are pseudonymised at most, not anonymised, so start from the view that it is.

## Who can do what

Shutter keeps no users or passwords of its own. A person signs in as an IRIS user, and what they may do comes from IRIS roles and resources checked by the API on the server ([Setup.cls:273-308](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L273-L308), [API/Dispatch.cls:18-76](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L18-L76)). Every Shutter role is restored to its defined permissions at each install ([Setup.cls:273](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L273)). All of this is Read.

- An **operator** reads every case, runs and resets scenarios, reinvestigates and may convene the board. An operator can also close an escalated, blocked or failed case by hand, unless the site's profile requires an approver ([API/Dispatch.cls:1010-1011](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L1010-L1011), [:1028](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L1028), [Store/SiteProfile.cls:33](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Store/SiteProfile.cls#L33)), can send a case's escalation email ([API/Dispatch.cls:831](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L831), [:884](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L884)) and can start a production review ([API/Dispatch.cls:1759](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L1759)). An operator can't approve, abandon, or save the profile ([API/Dispatch.cls:548](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L548), [:580](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L580), [:1054](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L1054), [:1207](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L1207), [:1368](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L1368)).
- An **approver** does all that, and approves or rejects, abandons a stuck case, retires precedents and saves the site profile, policy included ([Setup.cls:280-283](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L280-L283), [API/Dispatch.cls:1207](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L1207)). The approver of record is the signed-in user, never a name in the request ([API/Dispatch.cls:608](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L608)). By its definition an approver monitors the production and doesn't start or stop it ([Setup.cls:274-275](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L274-L275)); not tested on an instance.
- A **forwarder**, the user a watched production signs in as, can open a case through the intake route. It can call no other data route ([API/Dispatch.cls:1113](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L1113), [Setup.cls:306-308](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L306-L308)).
- An **MCP client** reads cases, evidence, plans and precedents, and writes nothing to a case or a receiver ([Publish/Tools.cls:303-305](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Publish/Tools.cls#L303-L305)). See the data flow for how far identifiers are tokens.
- The **public demo's logins** exist only when their passwords are given ([Setup.cls:340-344](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L340-L344)).

Every API request that makes a change needs the header `X-Requested-With: Shutter` ([API/Dispatch.cls:129](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L129)). Sign-in is the exception. An unauthenticated request receives an HTTP 401 response in JSON format, except at `/health`, which reports whether the instance is running, its version and the state of its production ([API/Dispatch.cls:255-265](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L255-L265)).

**The gate.** Every write Shutter intends passes a deterministic gate that the agents can't override ([Operation/Gate.cls:1-5](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Operation/Gate.cls#L1-L5)). A write needs a valid approval, from a person or under the site's written policy (recorded with the approver `policy`) for exactly this plan, on evidence that hasn't materially changed, at this receiver version; an approval expires after an hour and is void when the plan, the receiver's version, the site profile or the catalogue moves ([Store/Approval.cls:92-113](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Store/Approval.cls#L92-L113)). So an agent that has been misled or has made a mistake can only propose a plan. A board's plan always goes to a person, who may still approve a wrong one.

**One request reaches a receiver outside the gate:** an operator's preview, a dry run sent only to a receiver that declares it. A receiver that declares a dry run and writes anyway has taken a write ([API/Dispatch.cls:697](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L697), [:701-706](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L701-L706), [:728](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L728), [:737](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L737)).

## What a site still owes

None of these is a control in this repository. They are the site's to do, and a safety officer can tick them off.

**Clinical safety**

- [ ] Its own clinical safety case. In England, a site will be asked to carry out clinical risk management under DCB0160 as a deploying organisation and to decide who carries out the manufacturer's part under DCB0129. Neither part has been done for Shutter.
- [ ] Any regulatory classification, which depends on the site's intended use.
- [ ] Its judgement on how long a movement may stay unapplied: 24 hours of waiting, plus however long a person then takes.
- [ ] Whether the hazard rows above are the right ones for its setting.

**Data protection**

- [ ] A data protection impact assessment and information governance sign-off, covering case data to a model provider, NHS number and birth date by email, whole messages between namespaces or hosts, and any MCP client's own destination.
- [ ] The provider's terms: data use, prompt-cache retention, region.
- [ ] Retention: a purge for messages on a non-demo install; a decision on `PurgeClosedCases`, knowing that `CaseToken` and snapshots stay until it is on; escalation days.
- [ ] The decision whether `model_content.free_text` may ever be true.

**Install and configuration**

- [ ] Install with `-Ddemo=0`.
- [ ] The tier table, a stated `tier` and category on every receiver's entry, and one name per receiver or `namespace` on each hand-written entry.
- [ ] `FailureTimeout` 0 on any receiver with an API; `AlertOnError` on every receiver it wants watched; what "Completed" proves on each operation.
- [ ] `UncertainSettleSeconds` from its receiver's worst-case commit time.
- [ ] TLS on every route Shutter leaves to it: the forwarder, each connector, the mail adapter, the publisher's client, and the web server.
- [ ] A licensed instance behind its own edge, with rate limiting and a shielded `/health`.

**People and procedure**

- [ ] Who holds each IRIS role, with password policy, lockout and audit.
- [ ] Separation of duties, if wanted, through a role of its own: an install restores Shutter's roles, so editing them doesn't last.
- [ ] Who holds `Shutter_Scenarios` on a site install. The operator and approver hold it, and `POST /scenarios/reset` isn't limited to a demo install. From the code, it abandons open incidents ([API/Dispatch.cls:366-374](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/API/Dispatch.cls#L366-L374), [Scenarios/Runner.cls:399](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Scenarios/Runner.cls#L399), [Setup.cls:276](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L276), [:283](https://github.com/MxSalata/shutter/blob/v1.0.0/src/Shutter/Setup.cls#L283)). Read, not run.
- [ ] Someone watching the Workflow inbox and the case list, an operator who sends drafts, a team mailbox in the profile and its allowed domains.
- [ ] Who reads the evidence before approving, and who checks a drafted escalation before acting on it.
- [ ] A procedure to stop writes, naming who can stop the production.
- [ ] A rule for deaths and restricted records.
- [ ] Failover and restore, tested on its own setup.

**The receiver**

- [ ] That its API honours conditions and `dry_run`, and how it deduplicates.
- [ ] Whether a write through its API has the same effect at the receiver as a delivered message: its own onward feeds and its audit.
- [ ] Whether it refuses an occupied bed.
- [ ] What its ACK proves.

- Whether a site install behaves as read here: no instance installed with `-Ddemo=0` was used to write this page.
